# Session 096 - Persistence Endpoint Hardening

Date: 2026-02-24

## Objective
- Continue Phase 1 bulletproofing by hardening file/project persistence endpoints with stronger validation, abuse controls, idempotency, and usage telemetry.

## Changes Made

### Endpoints hardened
- `src/routes/api/upload-file/+server.js`
  - Added payload size guard and per-user rate limiting.
  - Added idempotency support (`Idempotency-Key`).
  - Added strict input checks for `imageData`.
  - Added sanitization for `filename` and `folder` path segments before storage path construction.
  - Added usage ledger writes (success/failure).

- `src/routes/api/replace-file/+server.js`
  - Added payload size guard and per-user rate limiting.
  - Added idempotency support.
  - Added strict validation for:
    - `imageData` type/size/data-url format
    - `existingUrl` URL format and allowed storage domains
  - Added ownership guard: extracted storage path must begin with `users/{uid}/`.
  - Added usage ledger writes.

- `src/routes/api/save-animation/+server.js`
  - Added payload size guard and rate limiting.
  - Added idempotency support.
  - Added strict frame validation using shared helpers:
    - bounded frame count
    - per-frame type/format/size checks
  - Added bounded FPS normalization.
  - Added usage ledger writes.

- `src/routes/api/save-project/+server.js`
  - Added payload size guard and rate limiting.
  - Added idempotency support.
  - Added stricter project/frame validation:
    - frame type/format/size checks
    - bounded frame count cap
    - bounded `fps` / `frameCount` normalization
    - sanitized `projectId` format
    - bounded `projectName`
  - Added usage ledger writes.

## Validation
- Lint checks run on all touched files: no new lint errors.

## Outcome
- Persistence routes now follow the same deterministic/retry-safe pattern as generation routes.
- Reduced risk from malformed payloads and path-injection style storage key construction.
- Expanded billing/audit telemetry coverage for save/upload operations.
